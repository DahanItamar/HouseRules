# HOUSE RULES — Design Lock Plan

## Context

`D:\Dev\repos\MyFirstGame` contains exactly one file: `Gemini-MD.md`, a strong but early concept doc for a 2D top-down retro casino hub with gambling mini-games, tiered progression, and a final showdown against "The House."

The goal of this phase is **not** to build the game. It is to expand that concept into a locked, implementable Game Design Document — deep enough that when code starts, every mechanic, number, screen, and input is already decided. Per the user's instruction: **no code, no Godot project, no scripts until the design is locked.**

Target platform is PC and the ROG Xbox Ally X. The Ally X runs Windows 11, so it is a PC — one Windows x64 build serves both. There is no console certification, no dev kit, no ID@Xbox. What the handheld *does* impose is a hard set of design constraints (7" 1080p at ~315 PPI, 500-nit IPS panel, controller-only input, battery budget) that must shape the art and UI now, because they are expensive to retrofit.

Two design problems drive this whole document and are called out explicitly below: **the RTP/progression contradiction** (§6) and **UI density at pixel-art resolution** (§7).

## 3. `01-CABINETS.md` — the cabinet catalog

The single most important structural decision: **every cabinet is described with the same spec template.** This makes them comparable, makes the economy math possible, and makes them drop-in implementable later without redesign.

### Spec template (applied to every machine)

| Field | Purpose |
|---|---|
| ID / Name / Tier | Registry key, display name, which floor it appears on |
| Fantasy | The 3-second pitch a player reads walking up to it |
| Arcade ancestor | What 80s/90s game it borrows its verbs from |
| Core loop | Bet → act → resolve, in one sentence |
| Rules & state machine | Every state, transition, and terminal condition |
| Agency class | Pure chance / chance+timing / chance+skill — determines whether RTP is fixed or skill-scaled |
| Bet range | Min/max per tier |
| RTP target | Return-to-player %, with the skill band where applicable |
| Volatility class | Low / medium / high — hit frequency vs. payout size |
| Max win | Cap as a multiple of stake |
| Paytable | Exact symbol/hand/outcome → payout mapping |
| Controller map | Every button, on gamepad first |
| Screen layout | Wireframe at the locked base resolution |
| Audio cues | Bet, anticipation, near-miss, win, loss |
| Art asset list | Sprites, animations, frame counts |
| Juice & tells | Near-miss framing, anticipation timing, celebration scaling |
| Edge cases | Insufficient chips, mid-round quit, max win, ties |

### Existing eight (from the concept doc)

Carried forward, each filled into the template: European Roulette, Blackjack 21, Video Poker, Dungeon Quest Slot, Vault Heist Slot, Pachinko/Plinko, Cyber-Race Terminal, Classic 3-Reel Retro Slot.

### New originals to design — arcade verbs × gambling odds

The concept doc asked for 3; the stronger move is to design a deeper bench and let the tier structure decide what ships. Each fuses a recognizable arcade mechanic with a real gambling math model.

| Cabinet | Arcade ancestor | Gambling hook |
|---|---|---|
| **Snake Eyes** | Snake | Eat dice pips to grow; each pip compounds the multiplier. Cash out any moment — or hit a wall and lose everything. Pure push-your-luck curve. |
| **Break the Bank** | Breakout / Arkanoid | Bricks are chip denominations, paddle lives cost chips, the vault behind the wall is the jackpot. Skill directly raises effective RTP. |
| **Card Invaders** | Space Invaders | Descending cards; shoot to collect a 5-card poker hand. Hand rank sets payout — but holding out for a flush lets the invaders reach the bottom. |
| **Minefield Vault** | Minesweeper / Mines | Grid reveal; each safe tile compounds, one mine ends it. Cheapest cabinet to build, highest tension per byte. |
| **Crosswalk** | Frogger | Advance lane by lane, multiplier rises per lane, one hit busts. The purest "cash out *now*?" instrument in the building. |
| **Jackpot Table** | Pixel pinball | Bumpers are multipliers, ramps spell J-A-C-K-P-O-T, the drain ends the round. Physics-driven variance. |
| **The Grabber** | Claw machine | A claw with a *visible* grip-strength meter — the cabinet openly displays its own house edge as a mechanic. Thematically the most honest machine in the casino. |
| **Beat the Dealer** | Rhythm / DDR | Note accuracy sets the payout multiplier; the dealer taunts on the off-beat. Skill-scaled RTP. |

Deliverable: all sixteen at catalog depth; the Main Floor set at full template depth, since those are built first.

## 4. `03-UX-FLOWS.md` — transitions and state machines

The concept doc's first open question. The floor-to-cabinet transition is the game's signature moment and needs to be specified frame by frame:

- **Approach** — proximity detection, cabinet highlight, attract-mode animation, button prompt appearing
- **Commit** — input, camera push-in, floor dimming, cabinet UI rising, audio duck and crossfade to machine-specific bed
- **Seated** — the cabinet owns the screen; bet selection, HUD persistence (chip count never disappears), how the floor is still implied at the edges
- **Resolve** — win/loss presentation, payout tally animation, chip counter roll
- **Exit** — reverse transition, re-anchoring the player sprite, returning floor ambience

Also specified: pause behavior mid-round, quitting with an active bet, insufficient-chip states, and the failure/empty/error states of every screen (what a cabinet shows when you can't afford its minimum, what the floor shows when a wing is locked).

## 6. `02-ECONOMY.md` — and the central math problem

**The contradiction to solve first.** Real casino machines run 92–97% RTP. Every machine having RTP below 100% means the player's bankroll mathematically trends toward zero — yet the game asks them to reach $1,000,000. Variance alone cannot carry a 15-hour campaign. This must be resolved by design, not discovered in playtesting. The proposed resolution:

1. **Skill machines** (Break the Bank, Card Invaders, Beat the Dealer) scale RTP from ~85% at novice play to **100–115% at mastery**. These are the reliable earners — the "job."
2. **Chance machines** (slots, roulette, Plinko) sit at 94–98%. These are where winnings get spent chasing big multipliers — the "thrill."
3. **Contracts** — The House issues objectives ("win three hands with a natural 21") paying flat chips. A guaranteed income floor independent of variance.
4. **Anti-ruin, as story.** Dropping below the minimum bet must never softlock the player. Instead: you take a **marker** from The House — a stipend that restores a floor amount and puts you in debt. Debt is the narrative engine that drives you toward the final showdown. Going broke advances the plot rather than ending the session.

Point 4 is the design's strongest idea and should be treated as a pillar, not a safety net.

**Also specified:** the full chip curve across three tiers (Main Floor 1–50 chip bets, bankroll 0→5k; High-Roller 50–2,500, 5k→100k; VIP Penthouse 1,000–50,000, 100k→1M), hit frequency and volatility per machine, expected session length per tier, cosmetic/suit unlock costs, and the target ~15–20 hour campaign pacing.

## 7. `06-ART-AUDIO-BIBLE.md` and `04-CONTROLS-HANDHELD.md`

**Base resolution: 960×540.** This is the decision most expensive to change later. It integer-scales exactly ×2 to 1080p (both your monitor and the Ally X) and ×4 to 4K, keeping pixel art crisp with no filtering. The tempting 640×360 is too tight for casino UI — a European roulette board has 37 numbered betting regions plus outside bets, and cannot be rendered legibly in 640 pixels. 960×540 buys the density these games need while still reading unmistakably as pixel art.

**Handheld constraints, locked now:**

- **Readability floor.** 1080p on a 7" panel is ~315 PPI at roughly 40cm viewing distance. Minimum body text 8px in 960×540 space; chip counts, bet amounts, and multipliers at 16px minimum. Verification method: view the game windowed at 50% on your monitor — if you can't read it there, it's unreadable in your hands.
- **Contrast floor.** A 500-nit IPS panel in a bright room crushes exactly the near-black neon aesthetic this game wants. Every critical UI element needs a luminance contrast floor against its background; neon glow is decoration layered *on top of* legible shapes, never the thing carrying the information.
- **Controller-first, no exceptions.** Every interaction must be completable on a gamepad. Roulette chip placement is the hard case and needs a designed snap-cursor that jumps between betting regions — not a free-floating mouse pointer with a stick glued to it.
- **Glyph swapping.** Prompts show Xbox glyphs on gamepad, key names on keyboard, switching on last-used device.
- **Battery.** 60 FPS cap and low-processor mode in menus and on the floor. A 2D casino game has no business draining a handheld battery.

**Art bible also covers:** neon-on-dark palette with the contrast floor baked in, Light2D usage for cabinet glow, optional CRT/bloom post-processing, character and cabinet sprite dimensions, UI grid and spacing, animation frame budgets.

**Audio direction:** jazz/synth beds shifting per tier, machine-specific stingers, and the deliberate psychology of win sounds — rising pitch on near-miss, payout tally scaling with win size.

## 8. `07-RESEARCH-NOTES.md`

- **Slot math primer** — RTP, hit frequency, volatility, weighted reel strips, and how paytables are actually constructed. Needed to write §6 credibly rather than guessing numbers.
- **Reference games** — Balatro (card-game juice and score escalation), Luck Be a Landlord (gambling-as-roguelite structure), Inscryption (the ominous dealer opposite you), Vampire Survivors (the compulsion loop), real coin-pusher and claw cabinets.
- **Ratings and storefront reality** — simulated gambling with no real-money wagering and no cash-out typically draws an ESRB *Simulated Gambling* descriptor and a PEGI *Gambling* descriptor, and is permitted on Steam. Practical constraint this places on design decisions being made now: **no real-money chip purchases and no cash-out mechanism**, which keeps the rating manageable and avoids gambling-regulation exposure entirely. Worth knowing before the economy is designed around it, not after.

Design work can't be unit-tested, so it's verified by review against specific criteria:

3. **The economy closes.** Walk the chip curve by hand: given the stated RTPs, bet limits, contract income, and marker stipend, can a player of average skill actually reach $1,000,000 in roughly 15–20 hours? If the arithmetic doesn't close, §6 is wrong and gets revised before anything else proceeds. This is the highest-risk item in the document.
4. **Readability check** — every wireframe in the docs is drawn at 960×540 and respects the 8px/16px minimums. Spot-check by scaling a mockup to 50% on your monitor.
5. **Controller completeness** — read `03-UX-FLOWS.md` end to end and confirm no flow anywhere requires a mouse.
6. **Read-through** — the GDD should be complete enough that a developer who has never seen the concept could build the Main Floor from it without asking a question. That's the bar for "locked."
